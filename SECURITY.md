# Security, call-cost controls, and operational limits

## Outbound-call endpoint

`POST /make-call` requires `CALL_SECRET` in the `X-Call-Secret` or `Authorization: Bearer` header. The destination is accepted only in the JSON body and is never returned by this endpoint. The secret must be set in the deployment's secret manager; do not put it in source, examples, URLs, issue reports, or logs. Twilio API errors and application logs are sanitized.

## Fail-closed controls

Calls are disabled unless `CALLS_ENABLED` is exactly `true`. The same kill switch is checked before outbound TwiML and before a Media Stream can open an OpenAI session. Missing or invalid safety configuration rejects the request. The defaults are one active call, five call attempts per rolling hour, twenty per rolling day, a maximum duration of 240 seconds, and destination prefixes `+52,+1`.

Destinations must be international E.164-style numbers. The accepted input may include spaces, parentheses, or hyphens, which are removed before sending the canonical number to Twilio. National-only numbers, extensions, malformed values, and countries outside the configured prefixes are rejected before contacting Twilio. The default `+1` and `+52` prefixes also enforce their ten-digit national-number length.

The concurrency and rate counters currently live in process memory. They are atomic within one process and suitable only for a single application replica. A restart resets the counters, and multiple Railway replicas would each enforce independent limits; the configured limits are per process/instance, not global. Keep one replica until a shared store replaces `InMemoryCallManager`. Reservations count toward hourly/daily attempts even when a later schedule or provider-readiness check blocks the call.

## Outbound commercial calling window

`/make-call` checks barriers in this order: authorization, enabled/valid safety configuration, request and destination/language, mission, in-process call limits, operating hours, required valid `RAILWAY_PUBLIC_DOMAIN`, provider readiness, then Twilio call creation. A failed local validation does not contact providers. Reservations are released from the active-call count if a later check blocks, while the attempt remains counted as described above. The operating-hours policy defaults to weekdays, 09:00–17:00 in `America/Mexico_City`; configure `CALL_OPERATING_TIMEZONE`, `CALL_ALLOWED_WEEKDAYS`, `CALL_OPERATING_START`, and `CALL_OPERATING_END` in the environment. Weekdays use full English names separated by commas; the start is inclusive and the end is exclusive. IANA time zones are evaluated with Python `zoneinfo`, including the selected zone's DST rules. Invalid policy settings fail closed. A blocked request returns and stores a structured reason and local window without storing the destination number. The policy currently covers weekly days and hours only; it does not implement national or company holiday calendars.

The status callback is protected with Twilio request-signature validation and releases a slot for terminal calls that never opened a media stream. Active media sessions also release their slot on completion, hold detection, duration limit, error, and disconnect. A timeout or connection exception while creating a Twilio call has an ambiguous outcome (Twilio may have accepted it before the response was lost), so that reservation is quarantined until the configured duration plus a short grace period rather than immediately allowing a potentially overlapping call. Other stale in-memory leases are also pruned after that bounded period.

## Duration and hold detection

`MAX_CALL_DURATION_SECONDS` defaults to and cannot exceed 240 seconds; lower positive whole-second values are supported. At the limit the app requests Twilio to complete the call, closes the Realtime WebSocket, and records `max_duration`.

Hold detection analyzes inbound Twilio μ-law audio. It requires at least 30 seconds of active audio and compares repeated two-second signal-feature windows over cycles up to 25 seconds. Brief silence does not count as hold. This is a conservative heuristic, not a universal music classifier: unusual hold music may be missed, and a sufficiently repetitive tonal signal can still produce a false positive.

## Mission configuration

`missions.json` defines the default mission and the allowed mission catalog. Each entry specifies its objective, relevant information to capture, relevance criteria, and possible follow-up actions. `MISSIONS_FILE` selects another catalog and `DEFAULT_MISSION_ID` selects its default entry. An authenticated `/make-call` request may select a mission by ID; only the ID is passed through the outbound Twilio URL and the selected definition is sent to Realtime as session instructions. Keep mission definitions free of secrets and confidential data. Mission instructions guide a natural conversation rather than a fixed script; follow-up actions are written as recommendations and are not executed automatically.

## Results and storage

At the end of a media session, the existing Realtime conversation is asked for a JSON report. The live call remains audio-only; the session switches to text output only after telephony ends to avoid adding text output to each live turn. The existing structured summary fields are retained, and the TXT report labels the summary as model-generated. The JSON and TXT also contain a speaker-labelled transcript assembled from completed caller transcription and assistant audio-transcript events. Input transcription uses `gpt-4o-mini-transcribe`; it is asynchronous, adds transcription usage, and may not exactly match what the realtime model understood. Caller transcript turns are placed in input-commit order because transcription completion events can arrive out of order. Values are accepted only as bounded strings or `null`; absent summary fields stay `null`. If Realtime is unavailable, the report uses null fields and the known terminal status, and marks the model summary unavailable. JSON and TXT files use random identifiers that contain no phone number or call SID. Known configured secret values and credential-shaped values are redacted before storing model-generated fields and transcript text. Transcript and report contents are never written to application logs; these files can contain sensitive conversation content and should be retained and accessed accordingly.

`CALL_RESULTS_DIR` selects the local output directory and defaults to `call_results/`, which is ignored by Git. Local filesystem storage is an implementation of the `CallResultStorage` interface, so it can be replaced by S3-compatible or database storage. Railway's local filesystem may be ephemeral across redeployments or restarts: these files are not permanent records until a persistent volume or remote storage backend is connected. A storage failure is logged only as a generic message and cannot guarantee a report file.

Each result with a configured `mission_id` also includes a deterministic `mission_state`. It merges transcript-supported mission fields from the prior local result for the same ID with the current Decision Engine and notification artifacts. It stores no transcript and invokes no model or provider. Completion requires every required mission field to have transcript-supported evidence across the accumulated state. User decisions take precedence as `waiting_for_user`; failed call setup is `blocked`; a relevant partial conversation is `in_progress`; a detected next step or inability to provide information is `needs_follow_up`; irrelevant calls do not complete the mission. The next call does not start automatically. The latest state is found by scanning JSON results in `CALL_RESULTS_DIR`; it therefore depends on that directory being available to the process. Legacy results without state remain readable, but are not retroactively reconstructed into cumulative state.

Mission approvals are recorded as per-mission decision records with stable IDs. `mission_decision.py` validates that the selected mission exists, matches both state and decision, and that the decision is still pending before recording `approved`, `rejected`, or `deferred`. The authenticated `GET /missions/{mission_id}/decisions` endpoint lists only pending decisions; the corresponding `/resolve` POST records a resolution into the latest matching JSON/TXT report, attributed to Fabian. Prior resolved records cannot be resolved again. An approval only records the operator's choice; this project does not execute the approved email, message, call, purchase, or other action. Legacy pending entries remain readable.

## Action/Approval Executor

`action_executor.py` is a local metadata and policy gate. Local record, analysis, draft, task, Mission State, and action-preparation actions may be marked `prepared`. External communication types require a linked formal Mission Decision and remain `awaiting_approval` until that exact decision for the same mission is resolved. Commercial commitments such as accepting terms/contracts, paying, or activating a service remain `blocked_by_policy`, including when an approval record says `approved`. Mission Decision resolution mirrors its status into the linked action metadata but has no executor and cannot transition an action to `executed`. `GET /missions/{mission_id}/actions` is authenticated with the existing `CALL_SECRET` and only reads local records. There is no action execution endpoint or provider client in this module; future delivery work must be implemented separately and must preserve these policy checks.

The model is instructed to use only stated details and return null for unsupported fields, but summaries still require human review before triggering business actions.

## Email drafts (not sent)

After Decision Engine, Notification Decision, and Mission State are computed, `email_draft.py` may create a local deterministic draft. A recipient is accepted only when the persisted `email` field is also marked by Decision Engine as a transcript-verified result and the exact address occurs in a `Contacto:` transcript turn. A draft also requires an actionable Decision Engine result, a positive Notification Decision, and supported facts, a contact request, or a verified next step. The body uses bounded, sanitized evidence and does not copy the full transcript. Every draft requires approval and is persisted with `sent=false`. `email_provider.py` defines a provider-neutral interface that receives only recipient lists, subject, and body; `email_provider_fake.py` implements it in memory and never uses a network or credentials. No real delivery provider exists in this release. Resolving a linked Mission Decision as approved may set `approval_status=approved_for_future_send`; `requires_approval` remains true and this status has no delivery effect. Rejected and deferred outcomes are recorded as metadata only. The authenticated read-only `GET /missions/{mission_id}/email-draft` endpoint returns only the persisted draft fields; old results without a draft remain readable and return not found from this endpoint.

Email actions pass through `action_executor.py` and `email_executor.py`. Only a registered `send_email` action whose linked Mission Decision is formally approved by Fabian can be considered. Before a non-dry-run attempt, the executor requires `EMAIL_ENABLED=true`, `EMAIL_DRY_RUN=false`, `EMAIL_PROVIDER=resend`, a configured valid `RESEND_FROM`, a nonempty `RESEND_API_KEY`, a matching injected Resend provider, a transcript-verified recipient, valid persisted draft metadata, and a SHA-256 digest matching the approved `to`, `cc`, `subject`, and `body`. The sender comes only from configuration. The Resend provider receives only recipient lists, subject, and body; errors are reduced to safe reason codes, and the API key is never included in results or logs. The local fake can simulate a production-shaped success in tests but never uses network or credentials. Execution results are stored once per action ID; provider failures are stored without success markers, and no automatic retries are made. This idempotency is protected by the local storage lock and applies only within one running process; it is not a cross-process or multi-replica guarantee. Use a shared transactional store before running multiple replicas. The authenticated `GET /missions/{mission_id}/actions/{action_id}/email-result` only reads the persisted result and never sends. There is no public email send endpoint. The example configuration remains in safe development mode: `EMAIL_ENABLED=false`, `EMAIL_DRY_RUN=true`, `EMAIL_PROVIDER=resend`, with empty Resend credentials.

WhatsApp actions use that same Action and Mission Decision registry. A positive Notification Decision records a pending WhatsApp approval in Mission State and creates one linked `send_whatsapp` action; it does not send or contact a provider. After Fabian formally approves that exact action, `whatsapp_executor.py` checks the persisted Notification Decision and Notification Message, validates the message again, and uses the existing adapter to require `WHATSAPP_ENABLED=true` plus a valid configured E.164 recipient. This flag only enables a local preview: even when true, the executor always records `provider=none`, `sent=false`, `dry_run=true`, and `executed_at=null`. No Twilio WhatsApp, Meta, HTTP, or socket client is present. Results are persisted by action ID without overwriting and the authenticated read-only `GET /missions/{mission_id}/actions/{action_id}/whatsapp-result` masks the destination number. No endpoint can send a WhatsApp message. Missing approval or invalid/disabled recipient configuration fails closed.

Each newly persisted result also includes a versioned `decision` object from `decision_engine.py`. The engine is pure local analysis: it has no credentials, provider clients, network access, or action executor. Caller utterances are kept as transcript quotes; structured fields are included as facts only when their value is present in the caller transcript. Mission findings count as supported only under the same check. The decision separates contact requests, information to provide, mission progress, recommendations, and approval requirements. It is a conservative Spanish/English keyword and exact-text matcher, not a general semantic verifier; review decisions before acting. Downstream integrations should consume this object and must still enforce its autonomy level. `AUTOMATIC` means safe to prepare or record locally, not permission for an external side effect; `REQUIRES_APPROVAL` must wait for Fabian, and `FORBIDDEN_AUTOMATIC` must never be carried out automatically. Older results without a `decision` remain readable.

## Protection against unexpected charges

Keep `CALLS_ENABLED=false` until an operator is ready to make calls. Use a dedicated Twilio number/account with spending limits and alerting, keep the app at one replica, and verify all safety settings before enabling calls. The app's in-memory limits are defense in depth and are not an account-wide Twilio spend cap. This project does not initiate calls while disabled and does not make automatic follow-up calls. Email delivery remains disabled in the example configuration and requires the separate explicit Resend production settings and formal action approval described above.

## Provider readiness and financial controls

`CALLS_ENABLED` is fail-closed: it must be exactly `true`, and `CALL_SECRET`, `OPENAI_API_KEY`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_PHONE_NUMBER` must all be present. Blank example values are intentionally not credentials. A clone without real configuration stays unable to create calls.

The authenticated, read-only `GET /health/dependencies` endpoint returns cached Twilio/OpenAI dependency states and safe operational alerts. It does not contact either provider. Before an outbound call passes the local barriers, the app makes bounded, read-only preflight requests: Twilio Account status and Balance resources, and OpenAI's documented Realtime model resource. These checks can identify inactive accounts, a non-positive Twilio balance, missing/invalid credentials, model-access failures, and provider errors. They are snapshots, not a guarantee that the next operation or a full call will be covered: positive Twilio balance does not establish the call's final cost or project spend-limit headroom, and OpenAI exposes no supported passive balance check here.

Provider errors are classified from documented HTTP statuses and error codes. Authentication, financial-limit, inactive-account, unavailable-model, and unclassified errors latch that provider unavailable in this process until a successful explicit readiness check. No provider operation is automatically retried. A Twilio create timeout has an ambiguous outcome and retains the existing bounded call reservation; the app does not repeat it. OpenAI Realtime errors end the dependent call, close the session, and skip a second OpenAI request for report generation; a fallback result still records the transcript and terminal status. Error text, request/response bodies, credentials, phone numbers, and conversation content are not included in alerts or logs.

Twilio status callbacks are not a reliable source of the financial cause of a failed call. For account-level usage notifications, configure Twilio Usage Triggers/Alarms in Twilio Console as a future operational control; this application does not create those resources or send notifications. Provider account spend caps, OpenAI project limits, billing state, and live external account changes still require review in the respective provider consoles.

Application logs do not include destination numbers, call bodies, authorization headers, tokens, model transcripts, report contents, or exception text from Twilio/OpenAI. Web server access logs should remain configured to omit request headers and bodies; the destination is in a POST body rather than the URL. Store OpenAI and Twilio credentials plus `CALL_SECRET` only as deployment secrets, rotate any credential that has been exposed, and do not print environment values when debugging.
